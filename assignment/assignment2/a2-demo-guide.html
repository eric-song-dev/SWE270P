Design decisions to mention值得一提的设计决策

Two steps with a human check in the middle
Misreading handwriting is the most likely failure, so the user confirms the code before it is analyzed.
Transcription never fixes bugs
If the model quietly corrected the code while reading it, the analysis would have nothing to find.
Structured JSON output
Pydantic schemas give each piece (summary, bugs, fixed code) its own field, so nothing is parsed out of free text.
One request per click, automatic retry on 429
Keeps the app inside the free-tier rate limits and avoids failing on a brief limit.
No API key in the notebook
Read from Colab Secrets or an environment variable.
Language as an enum
The model can only answer with one of the nine supported languages, so lookups never fail.
两步走，中间人工确认
最容易出错的是手写识别，所以分析之前先让用户确认代码。
转写时绝不修 bug
如果模型在读代码时顺手改了，分析环节就找不到 bug 了。
结构化 JSON 输出
用 Pydantic schema 让每部分（总结、bug、修复代码）各占一个字段，不需要从自由文本里解析。

Helpers: retry and fence stripping工具函数：重试与去除代码围栏

  • Every model call in the app goes through this function.
  • It tries up to max_retries = 3 times. Only an errors.APIError with code == 429 is retried.
  • The wait is 5 * (attempt + 1): 5 s after the first failure, 10 s after the second. That is linear backoff. A third 429 is raised.
  • Any other error (bad key, bad request, server error) is raised immediately, and the caller turns it into a gr.Error.

Why: on the free tier a short wait usually clears a per-minute limit, so retrying keeps the demo from failing on a brief spike.

  • 应用里所有模型调用都经过这个函数。
  • 最多尝试 max_retries = 3 次，只有 code == 429 的 errors.APIError 会重试。
  • 等待时间是 5 * (attempt + 1)：第一次失败等 5 秒，第二次等 10 秒，属于线性退避。第三次还是 429 就抛出。
  • 其他错误（key 无效、请求错误、服务器错误）立刻抛出，由调用方转成 gr.Error。

原因：免费额度下，稍等一下通常就能解除每分钟的限制，自动重试能避免 demo 因为短暂超限而失败。

  • Models often wrap code in ```python … ``` even when told not to. That would break the editor and the saved .py file.
  • strip("\n") removes only blank lines at the ends, so the first line keeps its indentation. rstrip() drops trailing whitespace.
  • If the first line starts with ``` it is dropped, and the same for the last line.
  • 即使明确要求不要加，模型也常把代码包在 ```python … ``` 里，这会破坏编辑器显示和保存的 .py 文件。
  • strip("\n") 只去掉首尾的空行，所以第一行的缩进得以保留；rstrip() 去掉末尾空白。
  • 第一行以 ``` 开头就删掉，最后一行同理。

cell 11 · code

Step 1: transcription第一步：转写

The shape of the reply: the language (restricted to the enum) and the code as text. Passing this class as response_schema makes Gemini return JSON with exactly these two fields.

回复的结构：语言（限定在枚举范围内）和代码文本。把这个类作为 response_schema 传入，Gemini 就会返回正好包含这两个字段的 JSON。

Each rule targets a specific failure:

  • Do NOT fix bugs. Otherwise the bugs silently disappear and the analysis has nothing to find.
  • 4 spaces per level. Indentation is syntax in Python, so it must be reproduced consistently.
  • Ignore paper lines, margins, crossed-out text. The photos are of lined notebook paper.
  • Ambiguous characters: pick the reading that is valid in the language ([ vs C, : vs ;, 1 vs l). This is where an LLM does better than plain OCR.
  • Code only, no fences, and the NO_CODE_FOUND sentinel for images without code.
  • {language_instruction} is filled in later with .format().

每条规则都针对一种具体的问题：

  • 不要修 bug。否则 bug 会悄悄消失，分析环节就找不到了。
  • 每级缩进 4 个空格。缩进在 Python 中是语法，必须一致地还原。
  • 忽略横线、页边、划掉的字。照片都是横线笔记本纸。
  • 有歧义的字符：选在该语言中合法的读法（[ 和 C、: 和 ;、1 和 l）。这正是 LLM 比普通 OCR 强的地方。
  • 只输出代码、不加围栏；图片里没有代码时返回 NO_CODE_FOUND 标记。
  • {language_instruction} 之后用 .format() 填入。
  1. No image uploaded: raise gr.Error right away, so no API call is wasted.
  2. Fill the prompt, then build a config with response_mime_type="application/json" and response_schema=Transcription.
  3. Send [image_file, prompt] as one request. The SDK accepts the PIL image directly. The image comes first, then the instructions.
  4. Transcription.model_validate_json parses and validates the reply. Any failure, from the API or from parsing, becomes gr.Error("Error during transcription: …").
  5. Strip fences as a safety net. An empty result or NO_CODE_FOUND gives a friendly "try a clearer photo" error.
  6. Return gr.update(...), which sets the editor's value, its syntax highlighting and its label (e.g. "Transcribed code (Java, editable)") in one go.
  1. 没有上传图片：直接抛 gr.Error，不浪费 API 调用。
  2. 填好 prompt，构建 config：response_mime_type="application/json"、response_schema=Transcription。

Q2Why did you split it into two steps instead of one call?为什么拆成两步，而不是一次调用完成？

Two reasons. Misreading the handwriting is the most likely failure, so we show the transcription first and let the user correct it. That way the analysis always runs on code the user has confirmed. It also keeps each prompt focused: the first one only reads, the second one only reviews. And each button is exactly one request, which helps with the free-tier rate limits.

两个原因。最容易出错的是手写识别，所以先展示转写结果，让用户修正，这样分析永远基于用户确认过的代码。另外每个 prompt 更专注：第一个只负责读，第二个只负责审查。而且每个按钮正好一次请求，有利于控制免费额度的速率限制。

Q3Why is the transcribed code editable?为什么转写出来的代码可以编辑？

Handwriting is ambiguous, and the model can misread a character, like a square bracket versus a C. If that happens, we don't want the analysis to report a bug that isn't in the original. An editable box keeps a human in the loop: fix the typo, then analyze.

手写有歧义，模型可能读错字符，比如方括号和字母 C。出现这种情况时，我们不希望分析报告一个原代码里并不存在的 bug。可编辑的代码框让人参与把关：先改掉误读，再分析。

Q16What's in your analysis prompt?分析 prompt 里写了什么？

Q17What does generate_with_retry do?generate_with_retry 是做什么的？

Every model call goes through it. It calls generate_content, and if the API returns a 429 rate-limit error, it waits and tries again: 5 seconds, then 10, for up to three attempts. Any other error, or a 429 on the last attempt, is raised so the user sees a clear message.

所有模型调用都经过它。它调用 generate_content，如果 API 返回 429 限流错误，就等待后重试：先 5 秒、再 10 秒，最多尝试 3 次。其他错误，或最后一次仍是 429，就直接抛出，让用户看到清楚的错误信息。

Q18If the reply is JSON, why do you still strip code fences?既然返回 JSON，为什么还要去掉代码围栏？

It's a safety net. Even inside a JSON string field, models sometimes wrap the code in ```python fences. That would break the code editor and the saved .py file, so strip_code_fences removes a leading and a trailing fence and keeps the indentation.

这是一道保险。即使在 JSON 的字符串字段里，模型有时也会把代码包在 ```python 围栏中。这会破坏代码编辑器和保存的 .py 文件，所以 strip_code_fences 去掉开头和结尾的围栏，同时保留缩进。

Q19Why is the language an Enum?为什么语言要用 Enum？

Because the enum becomes part of the JSON schema, the model can only answer with one of our nine language names. It can't return something like "python3". That guarantees the lookup in the LANGUAGES table always works, which gives us the right highlighter and file extension.

因为枚举会成为 JSON schema 的一部分，模型只能从 9 个语言名中选一个回答，不会返回 “python3” 之类的值。这保证了在 LANGUAGES 表里查找一定成功，从而拿到正确的高亮名称和文件扩展名。

Q20What does gr.update do?gr.update 是做什么的？

Returning gr.update instead of a plain value lets us change several properties of an output component at once. After transcription, we set the code, switch the syntax highlighting to the detected language, and update the label, for example to "Transcribed code (Java, editable)".

返回 gr.update 而不是普通值，可以一次修改输出组件的多个属性。转写之后，我们同时设置代码内容、把语法高亮切换成检测到的语言，并更新标签，例如 “Transcribed code (Java, editable)”。

Q21What happens if the JSON is invalid or the API call fails?JSON 无效或 API 调用失败会怎样？

model_validate_json raises a validation error, and the SDK raises its own API errors. Both are caught in the step function and re-raised as gr.Error, so the app shows a readable error message instead of crashing. The user can just click the button again.

model_validate_json 会抛出校验错误，SDK 也会抛出自己的 API 错误。两者都会在步骤函数里被捕获，再作为 gr.Error 抛出，所以应用会显示可读的错误信息而不是崩溃。用户再点一次按钮就行。

Q22Why raise gr.Error instead of returning an error string?为什么用 gr.Error 而不是返回错误字符串？

gr.Error shows a proper error popup in the UI and stops the event, so error text never ends up in the code editor or gets saved as code. We also use it for input checks, like no image, empty code, or no code found in the image, so we don't waste an API request.

gr.Error 会在界面上弹出正式的错误提示并中止该事件，错误文字不会出现在代码编辑器里，也不会被当成代码保存。我们还用它做输入检查，比如没上传图片、代码为空、图片里没有代码，避免浪费 API 请求。

With .click(fn, inputs, outputs). Gradio passes the current values of the input components as arguments, in order, and writes the return values into the output components.
